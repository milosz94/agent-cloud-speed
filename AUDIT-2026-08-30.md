## First: the one decision that gates everything (ITEM 1)

**ITEM 1 - Timing: makespan drops long cloud waits.  Status: DONE (option A, 2026-08-30)**

FIXED: transcript.py now charges a long (>300s) gap that ends in a PLATFORM event to platform (a blocking
cloud call's latency), not idle; only genuine agent/human pauses stay idle. +1 test, 485 green. Re-derived
the split in all 67 run JSONs from their saved transcripts (backup: acspeed-results/.split-backup-2026-08-30.tgz),
rebuilt all tables.json/txt, updated all 7 READMEs (matched rows by unchanged t-serve, replaced only platform/
agent). Result: makespan == t-serve for every run; platform+agent reconciles to t-serve in every published row
(gcp run14 platform 31.6s -> 1066s; serverless was under-reporting ~2.5x). SIDE EFFECTS: the false tool/README
headline "t-serve = platform + agent" now HOLDS (this also closes the two "false identity" findings under
statistics-ci and framing-anonymization), and Part-3 efficiency numbers were recomputed (makespan changed);
the paper's Part-3/5 numbers, when filled, must use the corrected makespan. Not committed yet.

--- original decision (kept for the record) ---

The instrument forces any gap > 300s (`DEFAULT_IDLE_CAP`, transcript.py:172) to owner `idle`, and
`operation.split()` computes `wall = platform + agent` which EXCLUDES `idle`. So a cloud-provisioning
call that blocks > 5 min is dropped from the reported `makespan_s`.

- Verified on gcp run14: two biggest spans are `idle` 544s + 490s = the agent blocking on a
  `run.googleapis.com` readiness poll and the Cloud Run build. The paper (p1body:56, p3body:194) says
  that blocking-poll cloud latency IS platform critical-path time. The instrument discards it.
- Effect: for 27 serverless runs, reported makespan under-measures true wall by median 2.49x (up to 5.38x).
  The true wall already exists in the code (`owner_split['makespan']` includes idle) but the JSON reports
  the idle-excluding number. Bites one fixed run too (aws-easy run4, 3.27x). Undisclosed in the paper.
- So the t-serve vs (platform+agent) gap is PLATFORM PROVISIONING WAIT, not "agent excess". Transcripts
  are all saved, so any fix is recomputable offline (no re-running deploys).

Choose one:
- **(A) Fix the instrument** - charge a gap that ends in a platform event to platform regardless of length;
  makespan then ~= wall; columns reconcile with NO extra column; most faithful to the paper. RECOMMENDED.
- **(B)** Report the idle-inclusive makespan (already computed) + disclose idle as a third term.
- **(C)** Keep the numbers, add a reconciling column named "provision wait" (not "agent-excess"), and
  disclose the 300s cap as a limitation.
